1. PROJECT OVERVIEW AND PURPOSE
================================================================================
- Name: OneMarket (evolved from LocalLoop codebase)
- Purpose: A full-stack hyperlocal marketplace web application dedicated to neighbourhood commerce in Hubballi, Karnataka. It connects verified local shopkeepers (merchants) across six distinct shopping zones with local residents.
- Problem Solved: Eliminates friction in neighbourhood purchasing by letting customers browse real inventory, compare prices across nearby stores, check stock availability, redeem reward tokens, and submit direct orders with official UPI payment verification or Cash on Delivery—without requiring manual phone calls or uncoordinated messaging.
- Architectural Model: 
  * Single Page Application (SPA) frontend served statically by Express.
  * Modular Node.js / Express REST API backend (`/api/*`).
  * Unified database layer supporting Supabase Postgres via `@supabase/supabase-js`, with an automated offline fallback adapter (`SupabaseOfflineAdapter`) and an active local MySQL connection pool for local persistence and backward compatibility.
  * Status: Implemented & Verified (all 4 automated test suites passing 100%).

9. ORDERS, TRACKING, CANCELLATION, AND INVENTORY
================================================================================
- Transactional Order Placement:
  * Implementation: `routes/orders.js` (`POST /api/orders`).
  * Transaction Integrity: Uses database transaction with row-level product locking (`FOR UPDATE` in SQL) to prevent race conditions and overselling.
  * Server Total Validation: Recalculates merchandise subtotal, delivery charges, taxes (5%), and token discounts server-side.
  * Atomic Inventory Deduction: `UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?`.
  * Automatic Cart Cleanup: Deletes ordered items from `cart_items` table upon successful order placement.
  * Status: Implemented. Verified in `test-backend.js` Tests 7, 9.
- Order Tracking Timeline:
  * Implementation: `routes/orders.js` (`GET /api/orders`), `js/views/orders-view.js`.
  * Milestone Progression: 5 discrete milestones (Pending -> Confirmed -> Packed -> Out for Delivery -> Delivered).
  * Audit Trail: Every transition is timestamped and recorded in `order_status_history`.
  * Status: Implemented. Verified in `test-backend.js` Test 8 and `test-e2e.js`.
- Self-Service Cancellation & Inventory Restock:
  * Implementation: `routes/orders.js` (`POST /api/orders/:id/cancel` and `PATCH /api/orders/:id/status`).
  * Eligibility Rule: Only active orders (`Pending`, `Confirmed`, `Accepted`, `Packed`) can be cancelled. Shipped, out-for-delivery, and completed orders are blocked from direct cancellation.
  * Inventory Restoration: Iterates through `order_items` and restores exact quantities back to `products.stock`.
  * Reward Token Rollback: Reverses tokens earned on the order (`CANCELLED_REVERSAL`) and refunds tokens redeemed by the customer (`REFUND`).
  * Status: Implemented. Verified in `test-backend.js` Test 15 and `test-e2e.js` Test 7.

- Endpoints:
  1. `GET /api/payments/config`: Exposes safe public parameters. Implemented.
  2. `POST /api/payments/create-order`: Generates a unique gateway order ID, verifies order total server-side, prevents duplicate payments, creates standard UPI intent URI (`upi://pay?pa=...`), generates mobile app-switch links, and inserts a pending payment record in `payments`. Implemented. Verified in `test-admin-payment.js` Test 7.
  3. `POST /api/payments/verify`: Verifies payment authenticity. Uses HMAC-SHA256 signature verification in live mode, or reference validation in sandbox mode. Atomically marks payment `Paid`, order `payment_status` `Paid`, updates order status to `Confirmed`, logs status history, and awards reward tokens. Implemented. Verified in `test-admin-payment.js` Test 8.
  4. `GET /api/payments/status/:orderId`: Polling endpoint used by the frontend modal every 3.5s to detect live background confirmation. Implemented.
  5. `POST /api/payments/webhook`: Asynchronous webhook listener verifying Razorpay `x-razorpay-signature` for `payment.captured` events. Implemented.
- Customer Payment User Interface:
  * Desktop Experience: Renders dynamic, scannable UPI QR code with a 5:00 countdown timer, instructions for PhonePe, GPay, Paytm, BHIM, CRED, and live polling indicator.

11. REWARDS, DISCOUNTS, AND PRICING
================================================================================
- Pricing Formula:
  * Merchandise Subtotal = Sum of (Item Unit Price * Quantity)
  * Token Discount = Tokens Redeemed * ₹1.00 (capped at max 50% of subtotal)
  * Delivery Fee = ₹0 for orders >= ₹500; ₹40 for orders < ₹500; ₹0 for Store Pickup
  * Taxes = Round(5% of Taxable Subtotal)
  * Grand Total = Max(0, Taxable Subtotal + Delivery Fee + Taxes)
  * Status: Implemented. Verified in `routes/orders.js` and `js/views/cart-view.js`.
- Promotional Discounts:
  * Product records store `price`, `original_price`, and `discount_percent`.
  * Frontend renders red promotional badges (e.g. "-20% OFF") and strike-through original prices.
  * Status: Implemented. Verified in catalogue and product views.
- Loyalty Rewards Token System:
  * Earn Rate: 1 token per ₹100 eligible spend.

13. AUTHENTICATION, AUTHORIZATION, AND SECURITY MEASURES
================================================================================
- Password Protection:
  * Algorithm: `bcryptjs` one-way hashing with salt rounds = 10 (`bcrypt.genSalt(10)`).
  * Storage: Plaintext passwords are never saved. Only `password_hash` is persisted.
  * Status: Implemented. Verified in `routes/auth.js` and `test-backend.js`.
- Session Management:
  * Standard: JSON Web Tokens (JWT) signed via `jsonwebtoken`.
  * Expiration: 7 days (`{ expiresIn: '7d' }`).
  * Secret: Read from `JWT_SECRET` environment variable with fallback.
  * Client Storage: Stored in browser `localStorage` under `onemarket_auth_token`. Transmitted via `Authorization: Bearer <token>` HTTP header.
  * Status: Implemented. Verified in `middleware/auth.js` and `test-backend.js`.
- Role-Based Access Control (RBAC):
  * Defined Roles: `customer`, `seller`, `admin`.
  * Registration Protection: Public endpoints (`register-customer` and `register-seller`) hardcode role to `customer` or `seller`. Admin accounts cannot be created via public registration.
  * Route Guards:
    - `requireAuth`: Enforces valid JWT token (returns 401 Unauthorized).
    - `requireRole(...roles)`: Enforces exact role membership (returns 403 Forbidden).
    - `requireCustomer`: Guard for cart operations and review submissions.
    - `requireSeller`: Guard for merchant inventory CRUD and order fulfillment.
    - `requireAdmin`: Guard for platform stats, user suspension, product moderation, and audit logs.
  * Status: Implemented. Verified in `test-backend.js` Test 12 and `test-admin-payment.js` Tests 1, 2.
- Web Application Security:
  * SQL Injection Prevention: 100% of database queries use parameterized prepared statement placeholders (`?`).
  * Cross-Site Scripting (XSS) Prevention: All dynamic text outputs in templates are passed through `Utils.escapeHTML()`.
  * CORS Configuration: Standard CORS middleware enabled on Express.
  * Error Handling: Centralized error handler (`middleware/error-handler.js`) prevents sensitive stack trace leakage to clients.
  * Gateway Secret Protection: Razorpay secret and database credentials are never transmitted to client JavaScript.
